# 전시 일정 · 접근성 자료 적용 (on) 실행 결과

푸른숲미술관 전시 네 건을 전시 이름과 관람 요일로 찾는 화면을 국내 접근성 자료(KWCAG 2.2, NIA 제작기법)에 맞춰 개선한 결과입니다. [기본 개발 (off)](/?demo=2026-11-27-exhibition-filter-off) 화면을 복사한 뒤, 자료를 조회해 적용하는 개발 절차를 켜고 같은 요청서 기준으로 고쳤습니다.

확장 검사에서 off의 명도 대비 위반(결과 건수 2.32:1)이 사라졌습니다. 판정 보류 요소 두 개는 off와 같이 남았습니다. 코드에서 바뀐 것은 결과 건수와 placeholder의 글자색, 검색란의 숨김 레이블, 상태 영역의 범위입니다. 보이는 레이블이 없는 구성, Tab 순서, 320px 화면, 마크업 검사 결과는 off와 같았습니다.

## 사용 방법

- 검색란에 전시 이름의 일부를 입력하거나 요일을 고른 뒤 돋보기 버튼을 누르거나 Enter를 누릅니다. 목록과 결과 건수가 바뀝니다.
- 요일을 바꾸기만 해서는 결과가 바뀌지 않습니다. 검색을 실행해야 바뀝니다.
- ↺ 버튼을 누르면 조건이 지워지고 전시 네 건이 다시 보입니다. 초점은 검색란으로 갑니다.
- 조건에 맞는 전시가 없으면 ‘총 0건’과 ‘조건에 맞는 전시가 없습니다’가 표시됩니다.
- off 화면과 나란히 열어 결과 건수 ‘총 4건’과 검색란 안내 문구의 글자색을 비교합니다.

## 요청서와 조정한 부분

개발 에이전트에게 준 ‘화면 요청서: 전시 일정’의 전문입니다.

> ### 공통 사항
>
> 가상의 기관 ‘푸른숲도서관’(전시 일정은 ‘푸른숲미술관’)의 화면입니다. HTML, CSS, JavaScript만 쓰고 외부 라이브러리와 CDN은 쓰지 않습니다. 모든 파일은 지정한 데모 폴더 안에 두고, 진입 페이지는 `index.html`입니다. 페이지 제목은 `<화면 이름> - 한국 웹 접근성 플레이그라운드`, 설명(meta description)은 요청서에 적은 문장을 씁니다. 데스크톱과 폭 320px 화면에서 모두 쓸 수 있어야 합니다. 결과 문서는 다른 담당자가 쓰므로 만들지 않습니다.
>
> ### 요청 내용
>
> 설명: 전시 이름과 관람 요일로 전시 일정을 찾습니다.
>
> 전시 네 개를 보여 주고 이름과 요일로 찾습니다. 전시는 ‘종이로 만든 풍경’(수 14:00, 제1전시실), ‘색으로 읽는 도시’(토 11:00, 제2전시실), ‘종이 위의 정원’(토 15:00, 열린 작업실), ‘주말에 만나는 판화’(일 13:00, 제1전시실)입니다. 이름 검색란, 요일 선택(전체·수·토·일), 검색 버튼, 초기화 버튼이 있습니다. 결과 건수를 표시하고, 결과가 없으면 ‘조건에 맞는 전시가 없습니다’를 보여 줍니다.
>
> 디자인 시안: 검색란은 안내 문구 ‘전시 이름 검색’만 둡니다. 요일 선택은 제목 없이 첫 항목을 ‘요일’로 둡니다. 검색 버튼은 돋보기 아이콘, 초기화는 ↺ 아이콘입니다. 결과 건수 ‘총 4건’은 13px `#aaaaaa`입니다.

개발 에이전트는 바꾼 것이 세 가지이고 모두 접근성 개선이라고 보고했습니다. 근거 구분은 보고서를 따랐습니다.

| 요청서 시안 또는 off의 구현 | 조정한 내용 | 이유 |
| --- | --- | --- |
| 결과 건수 13px, `#aaaaaa` | 색을 `#595959`로 바꿨습니다. 13px과 문구는 시안대로 두었습니다. | 보고서는 시안의 색이 흰 배경에서 2.32:1이라 5.4.3의 4.5:1(KWCAG 요구사항)에 못 미치고, 바꾼 색은 7.00:1이라고 적었습니다. |
| 검색란의 숨김 레이블 ‘전시 이름 검색’ | ‘전시 이름’으로 바꿨습니다. 화면에 보이는 모습은 같습니다. | 안내 문구(placeholder)와 같은 문장이 겹치지 않게 하려는 조정입니다(7.3.2). |
| 결과 건수만 상태 영역 | 결과 건수와 ‘조건에 맞는 전시가 없습니다’를 하나의 `role="status"` 영역으로 묶었습니다. | off는 건수만 안내 영역에 있어 결과가 없을 때의 문구를 보조기술이 알리지 못한다고 보고서가 적었습니다. `role="status"`의 동작은 자료 밖 근거(WAI-ARIA)입니다. |

보고서는 적용 기준 표의 5.4.3 항목에 안내 문구(placeholder)의 색을 `#595959`로 명시한 것도 함께 적었습니다. 코드에는 이 변경까지 네 가지가 들어 있습니다.

시안 가운데 유지한 부분은 다음과 같습니다.

- 레이블이 보이지 않는 구성(안내 문구만 있는 검색란, 첫 항목이 ‘요일’인 선택 상자)은 그대로 두었습니다. 보고서는 숨김 레이블로 이름을 제공해 요구사항을 충족한다고 판단했습니다.
- 요일 선택의 첫 항목 ‘요일’은 요청서 본문의 ‘전체’와 표기가 다릅니다. 시안대로 두었고, 값이 비어 있어 전체 전시를 보여 줍니다.
- 두 아이콘 버튼은 보이는 글자가 없어 `aria-label`로 이름을 제공합니다.

개발 에이전트는 접근성과 무관한 기능 결함을 찾지 못했고 고친 것도 없다고 보고했습니다. 필터 로직을 Node로 실행해 ‘토’ 2건, ‘종이’ 2건, ‘종이 위’와 ‘토’ 1건, ‘없는’ 0건을 확인했다고 적었습니다. 더하면 좋을 기능의 제안은 없었습니다.

## 개발 조건

- 모델과 실행 도구: off와 같은 Claude Sonnet 5.5, Claude Code 2.1.332(헤드리스 실행). 개발 세션은 대화 턴 36회, 101초였습니다.
- 실행 위치: 이 저장소 밖의 빈 폴더입니다. 그래서 이 저장소의 프로젝트 지침은 읽지 않았습니다.
- 개발 절차: off 화면을 복사한 폴더에서 국내 접근성 자료를 조회해 적용하는 절차를 켰습니다. 복사한 것은 초기화 버튼 결함을 고친 뒤의 off 화면입니다.
- 지시: 같은 요청서 기준으로 화면을 개선하게 했습니다. 요청서 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 요청자가 미리 승인했습니다. 질문하지 말고 개선까지 마치게 했습니다.
- 자료 조회: 설정 확인, 절차 문서, 자료 목록, 레코드 순서로 읽었습니다. 자료 조회 명령 21회는 모두 주소 하나에 명령 하나인 같은 형태였고, 실패한 조회는 없었습니다. KWCAG 레코드 16개와 NIA 사례 레코드 4개를 읽었습니다. 화면 종류와 관계없이 고르는 12개 항목(5.3.2, 5.4.1, 5.4.3, 5.4.4, 6.1.1, 6.1.2, 6.1.3, 6.4.2, 6.5.3, 7.1.1, 7.2.1, 8.1.1)의 레코드를 모두 받았습니다.
- 도구: 브라우저 도구와 MCP 서버가 없었고, 디자인 검사 플러그인을 껐습니다. 그래서 개발 에이전트는 코드와 명령으로만 확인했습니다. 허용한 셸 명령은 `node`, `ls`, `cat`, `curl`, `mkdir`, `cp`입니다. 폴더를 옮긴 뒤 다른 명령을 잇는 복합 명령 2건이 거부됐습니다. 보고서에 이 거부 때문에 하지 못했다고 적은 작업은 없습니다.
- 수정 요청: on 화면에는 결함 보고를 보내지 않았습니다.
- 보존: on 개발 뒤에도 off 화면의 파일이 바뀌지 않았음을 해시로 확인했습니다.
- 재실행: 이 문서는 세 번째 실행의 결과입니다.
  1. 첫 실행에서는 다른 모델(Claude Opus 5.5)로 이 저장소 안에서 off 화면 13개를 만들었습니다. 13개 모두 확장 검사 위반이 0건이었고, 개발 에이전트들은 이 저장소의 프로젝트 지침과 일반 지식에 따라 시안을 접근성 기준에 맞춰 바꿨다고 보고했습니다. on 화면은 만들지 않았습니다.
  2. 두 번째 실행(2026-11-27 오후)에서는 모델과 실행 위치를 바꿔 다시 만들었습니다. off 개발 에이전트 13개 중 12개가 절차의 설정을 읽는 명령에서 자료 목록(검사항목 33개의 제목과 주소)을 함께 받았습니다. on 13개는 모두 일괄 내려받기 명령이 거부됐고, 일부는 필수 항목의 본문을 끝까지 읽지 못했습니다.
  3. 세 번째 실행(2026-11-27 밤)에서는 개발 절차를 설정 확인 문서와 절차 문서로 나눠 off 세션이 절차와 자료를 보지 않게 했고, 자료 조회 명령을 한 형태로 고정했습니다. 요청서는 두 번째 실행과 같은 확정본이고, 화면은 처음부터 다시 만들었습니다.

### NIA 제작기법 권장 사항

- 보고서는 7.3.2 항목 안에서 두 가지를 권장 사항으로 나눠 적었습니다. 안내 문구만으로 레이블을 대신하지 않는 것과, 선택 상자의 첫 옵션이 레이블 역할을 하지 못한다는 점입니다.

### 자료 밖 근거

- 상태 영역: 결과 건수와 결과 없음 문구를 묶은 `role="status"`의 변경 안내 동작은 WAI-ARIA 명세에 의존한다고 보고서가 적었습니다. [status 역할](https://www.w3.org/TR/wai-aria-1.2/#status)
- 숨김 레이블: 화면에서만 숨기는 `sr-only` CSS 기법입니다. 이 기법을 정한 단일 표준은 없습니다.

## 검증 결과

Playwright 1.66 스크립트가 실행한 헤드리스 Chrome 158.0.8127.37(창 크기 1280×900)에 KWCAG 검사 0.1.17 확장의 검사 스크립트(axe-core 4.14.1 포함)를 확장과 같은 순서로 주입해 검사했습니다. 확장의 사이드 패널 화면은 쓰지 않았습니다. 마크업은 확장의 마크업 검사와 같은 html-validate 10.17.1 규칙으로 검사했습니다. 마우스와 키보드 조작은 사람이 아니라 스크립트가 보냈습니다. 규칙 수는 ‘위반 / 판정 보류 / 통과’ 순서이고, 요소 수가 아니라 규칙 종류 수입니다. off의 수치는 초기화 버튼을 고친 수정본에서 잰 것입니다.

### 브라우저에서 관찰한 결과

- off의 결과 건수는 측정 대비 2.32:1로 color-contrast 위반이었습니다. on에서는 위반이 없었습니다.
- 판정 보류 요소 두 개는 두 화면이 같았습니다. off에서는 color-contrast가 위반 규칙으로 집계돼 판정 보류 규칙 수가 1이었고, on에서는 2였습니다. 통과 규칙 수는 두 화면이 같았습니다.
- ‘없는전시’를 입력하고 Enter를 누르면 두 화면 모두 목록이 비고 ‘총 0건’과 ‘조건에 맞는 전시가 없습니다’가 표시됐습니다. on에서는 두 문구가 모두 `role="status"` 영역 안에 있었습니다.
- ↺ 버튼을 누르면 두 화면 모두 검색란이 비워지고 전시 네 건과 ‘총 4건’이 다시 보였습니다. 초점은 검색란으로 갔습니다.
- ‘종이’를 입력하고 토요일을 고른 뒤 검색 버튼을 누르면 두 화면 모두 전시 한 건과 ‘총 1건’이 표시됐습니다.
- 두 화면 모두 검색란과 요일 선택의 레이블이 화면에서 숨겨져 있었습니다.
- 두 화면 모두 Tab 순서가 같았고, 초점 표시가 없는 정지점은 없었습니다.

### 코드에서 확인한 사실

- `script.js`는 off 수정본과 같습니다. 초기화 버튼의 `id`도 `clear-btn`입니다.
- `index.html`: 검색란의 숨김 레이블이 ‘전시 이름’으로 바뀌었습니다. `role="status"`가 결과 건수 문단에서 그 문단과 결과 없음 문단을 감싼 `div`로 옮겨졌습니다. 결과 없음 문단은 목록 뒤에서 목록 앞으로 옮겨졌습니다. `id`는 7개이고 중복이 없습니다.
- `style.css`: `.count`의 색이 `#595959`로 바뀌었고 `input::placeholder{color:#595959;opacity:1}`이 추가됐습니다. 그 밖의 규칙은 off와 같습니다.
- 요일 선택의 항목은 off와 같이 ‘요일’(값 없음), ‘수’, ‘토’, ‘일’ 네 개입니다.

## 미검증 항목

- 스크린 리더 발화: 검색이나 초기화 뒤 ‘총 N건’과 ‘조건에 맞는 전시가 없습니다’를 읽어 주는지 확인하지 않았습니다. 보고서는 숨김 상태에서 나타나는 문구의 안내 여부가 보조기술마다 다를 수 있다고 적었습니다.
- 200% 확대에서 가로 스크롤이 생기는지 확인하지 않았습니다. 폭 320px에서 가로 스크롤이 없다는 것만 확인했습니다.
- 바꾼 색의 대비 7.00:1은 보고서의 계산값입니다. 브라우저에서는 확장 검사에 위반이 없다는 것만 확인했습니다.
- 판정 보류 두 요소가 실제 문제인지는 이 문서에서 판단하지 않았습니다.
- 요일만 바꾸고 검색을 실행하지 않았을 때 결과가 그대로인지는 코드로만 확인했습니다.
- 실제 터치 기기, Chrome 이외의 브라우저, 검색 0건 상태의 320px 화면은 확인하지 않았습니다.
