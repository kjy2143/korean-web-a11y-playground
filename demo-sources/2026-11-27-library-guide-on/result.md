# 도서관 이용 안내 · 접근성 자료 적용 (on) 실행 결과

공통 헤더의 메뉴 10개와 검색, 회원 가입·대출·반납 안내 본문으로 이루어진 이용 안내 페이지를 국내 접근성 자료(KWCAG 2.2, NIA 제작기법)에 맞춰 개선한 결과입니다. [기본 개발 (off)](/?demo=2026-11-27-library-guide-off) 화면을 복사한 뒤, 자료를 조회해 적용하는 개발 절차를 켜고 같은 요청서 기준으로 고쳤습니다.

확장 검사에서 off의 판정 보류(메뉴 글자 9개의 명도 대비, 측정 3.45:1)가 사라졌습니다(off 0 / 1 / 28, on 0 / 0 / 29). on은 메뉴 글자색을 시안의 `#8a8a8a`에서 `#666`으로 바꿨습니다. ‘본문 바로가기’ 링크를 Enter로 실행한 뒤 초점을 가진 요소는 off에서 `body`, on에서 `main`이었습니다.

## 사용 방법

1. 페이지를 열고 Tab 키를 처음 누르면 왼쪽 위에 ‘본문 바로가기’ 링크가 나타납니다. Enter를 누르면 초점이 본문(`main`)으로 옮겨집니다.
2. 헤더에는 텍스트 로고 ‘푸른숲도서관’, 검색 입력란과 돋보기 버튼, 메뉴 10개가 있습니다. 로고와 메뉴의 주소는 `#`입니다.
3. 메뉴 글자는 off보다 진한 회색(`#666`)입니다. 현재 메뉴 ‘이용 안내’는 초록색 굵은 글씨로 표시됩니다.
4. 검색 양식에는 `onsubmit="return false"`가 있어 제출해도 다른 화면으로 이동하지 않게 만들어졌습니다.
5. 본문은 ‘이용 안내’ 제목 아래 ‘회원 가입’, ‘대출’, ‘반납’ 소제목과 문단으로 이루어지고, 아래에 도서관 주소가 있는 푸터가 있습니다.

## 요청서와 조정한 부분

개발 에이전트에게 준 ‘화면 요청서: 도서관 이용 안내’의 전문입니다.

> ### 공통 사항
>
> 가상의 기관 ‘푸른숲도서관’(전시 일정은 ‘푸른숲미술관’)의 화면입니다. HTML, CSS, JavaScript만 쓰고 외부 라이브러리와 CDN은 쓰지 않습니다. 모든 파일은 지정한 데모 폴더 안에 두고, 진입 페이지는 `index.html`입니다. 페이지 제목은 `<화면 이름> - 한국 웹 접근성 플레이그라운드`, 설명(meta description)은 요청서에 적은 문장을 씁니다. 데스크톱과 폭 320px 화면에서 모두 쓸 수 있어야 합니다. 결과 문서는 다른 담당자가 쓰므로 만들지 않습니다.
>
> ### 요청 내용
>
> 설명: 공통 메뉴와 검색이 있는 이용 안내 페이지입니다.
>
> 공통 헤더에 텍스트 로고 ‘푸른숲도서관’, 메뉴 10개(도서관 소개, 이용 안내, 자료 검색, 전자도서관, 프로그램, 열람실, 공지사항, 자주 묻는 질문, 오시는 길, 마이페이지), 검색이 있습니다. 메뉴 주소는 `#`입니다. 본문은 ‘이용 안내’ 제목 아래 ‘회원 가입’, ‘대출’, ‘반납’ 소제목과 소제목마다 두 문단입니다. 아래에 도서관 주소가 있는 푸터를 둡니다.
>
> 디자인 시안: 헤더 검색은 입력란(안내 문구 ‘검색어 입력’)과 돋보기 아이콘 버튼입니다. 메뉴 글자는 15px `#8a8a8a`, 현재 메뉴(이용 안내)는 초록색입니다. 시안에 그려진 요소 외에는 화면에 보이지 않게 해 주세요.

요청자는 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 미리 승인했습니다. 개발 에이전트가 조정한 내용과 보고서에 적은 이유는 다음과 같습니다.

| 요청서 또는 off 화면 | on 화면 | 보고서에 적은 이유 |
| --- | --- | --- |
| 메뉴 글자 15px `#8a8a8a` | 15px `#666` | `#8a8a8a`는 흰 배경에서 대비가 약 3.45:1이라 15px 일반 글자의 기준 4.5:1에 못 미칩니다(5.4.3). `#666`은 약 5.74:1입니다. |
| 건너뛰기 링크의 이동 대상 `<main id="main">` | `tabindex="-1"`을 더했습니다. `main:focus { outline: none; }`도 더했습니다. | 링크를 누르면 초점이 본문 시작으로 옮겨 갑니다(6.4.1). `main`은 조작 요소가 아니라서 초점 테두리를 숨겼습니다. |
| 검색창 테두리 `#999` | `#767676` | 흰 배경 대비가 약 4.54:1입니다. 요구사항 항목에 직접 걸리는 부분은 아니고, 입력란 경계를 더 잘 보이게 하려는 조정이라고 적었습니다. |

시안대로 둔 부분과 보고서의 판단은 다음과 같습니다.

- 현재 메뉴의 초록색 `#1b6b35`(보고서 계산 약 6.5:1)와 굵은 글씨는 그대로 두었습니다. 보고서는 현재 메뉴가 색뿐 아니라 굵기와 `aria-current="page"`로도 구분된다고 적었습니다.
- 보고서는 ‘시안에 그려진 요소 외에는 보이지 않게’ 하라는 요청과 요구사항이 부딪치는 곳이 둘이라고 적었습니다. 검색 입력란의 레이블 ‘검색어 입력’은 화면에서 숨기고 보조기술에는 읽히게 두었습니다. 건너뛰기 링크는 평소에는 숨기고 키보드 초점을 받을 때만 보이게 두었습니다. 두 처리 모두 off와 같습니다.
- 안내 문구(placeholder) ‘검색어 입력’은 시안대로 유지했습니다.
- 보고서는 접근성과 무관한 기능 결함을 찾지 못했고 고친 것이 없다고 적었습니다.
- 보고서는 검색 결과를 보여주는 동작과 빈 검색어 안내를 더하면 좋을 기능으로 제안했습니다. 요청서에 없어 구현하지 않았습니다.

## 개발 조건

- 모델과 실행 도구: off와 같은 Claude Sonnet 5.5, Claude Code 2.1.332(헤드리스 실행)
- 실행 위치: 이 저장소 밖의 빈 폴더입니다. 그래서 이 저장소의 프로젝트 지침은 읽지 않았습니다.
- 개발 절차: off 화면을 복사한 폴더에서 국내 접근성 자료를 조회해 적용하는 절차를 켰습니다.
- 지시: 같은 요청서 기준으로 화면을 개선하게 했습니다. 요청서 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 요청자가 미리 승인했습니다. 질문하지 말고 개선까지 마치게 했습니다.
- 자료 조회: 설정 확인, 절차 문서, 자료 목록, 레코드 순서로 읽었습니다. 자료 조회 명령은 21회였고 모두 주소 하나에 명령 하나인 같은 형태였습니다. 조회에 실패한 주소는 없었습니다. 화면 종류와 관계없이 고르는 12개 항목(5.3.2, 5.4.1, 5.4.3, 5.4.4, 6.1.1, 6.1.2, 6.1.3, 6.4.2, 6.5.3, 7.1.1, 7.2.1, 8.1.1)에 5.1.1, 6.4.1, 6.4.3, 7.3.2를 더해 KWCAG 레코드 16개를 받았습니다. NIA 사례 레코드는 2.4.1과 2.4.3의 적용 사례와 개선 필요 사례 4개를 받았습니다.
- 도구: 브라우저 도구와 MCP 서버가 없었고, 디자인 검사 플러그인을 껐습니다. 그래서 개발 에이전트는 코드와 명령으로만 확인했습니다. 허용한 셸 명령은 `node`, `ls`, `cat`, `curl`, `mkdir`, `cp`입니다. 이 세션에서는 셸 호출 2건이 거부됐고 둘 다 `python3` 명령이었습니다. 개발 에이전트는 명도 대비를 손으로 계산했고, 마크업 짝과 중첩을 검사하는 Python 스크립트를 돌리지 못해 태그 짝을 파일을 읽어 확인했다고 보고했습니다.
- 수정 요청: 이 화면에는 결함 보고를 보내지 않았습니다.
- 보존: on 개발 뒤에도 off 화면의 파일이 바뀌지 않았음을 해시로 확인했습니다.
- 재실행: 이 문서는 세 번째 실행의 결과입니다.
  1. 첫 실행: 다른 모델(Claude Opus 5.5)로 이 저장소 안에서 off 화면 13개를 만들었습니다. 13개 모두 확장 검사 위반이 0건이었고, 개발 에이전트들은 이 저장소의 프로젝트 지침과 일반 지식에 따라 시안을 접근성 기준에 맞춰 바꿨다고 보고했습니다. on 화면은 만들지 않았습니다.
  2. 두 번째 실행(2026-11-27 오후): 모델과 실행 위치를 바꿔 다시 만들었습니다. off 개발 에이전트 13개 중 12개가 절차의 설정을 읽는 명령에서 자료 목록(검사항목 33개의 제목과 주소)을 함께 받았습니다. on 13개는 모두 일괄 내려받기 명령이 거부됐고, 일부는 필수 항목의 본문을 끝까지 읽지 못했습니다.
  3. 세 번째 실행(2026-11-27 밤): 개발 절차를 ‘설정 확인’ 문서와 ‘절차’ 문서로 나눠 off 세션이 절차와 자료를 보지 않게 했고, 자료 조회 명령을 한 형태로 고정했습니다. 요청서는 두 번째 실행과 같은 확정본입니다. 화면은 처음부터 다시 만들었습니다.

### NIA 제작기법 권장 사항

보고서는 아래 네 항목에서 요구사항과 권장 사항을 나눠 적었습니다.

- 6.4.1: 건너뛰기 링크의 이동 대상 처리(`tabindex="-1"`)는 사례를 따른 권장 사항으로 분류했습니다. 보고서가 든 사례는 NIA 2.4.1의 [개선 필요 사례](https://kwcag-docs.fe4all.dev/browse#v1/criteria/nia-2.4.1-s5.json) 5입니다. 같은 항목의 [적용 사례](https://kwcag-docs.fe4all.dev/browse#v1/criteria/nia-2.4.1-s4.json)도 읽었습니다.
- 6.4.3: 아이콘 링크 처리는 사례를 따른 권장 사항으로 분류했습니다. 보고서가 든 사례는 NIA 2.4.3의 [적용 사례](https://kwcag-docs.fe4all.dev/browse#v1/criteria/nia-2.4.3-s4.json) 3입니다. 같은 항목의 [개선 필요 사례](https://kwcag-docs.fe4all.dev/browse#v1/criteria/nia-2.4.3-s5.json)도 읽었습니다.
- 6.1.3: 조작 요소의 크기 수치는 권장 사항으로 분류했습니다.
- 5.1.1: 기능 이미지 처리(돋보기 아이콘)는 NIA 기본 규칙을 따른 권장 사항으로 분류했습니다.

### 자료 밖 근거

- 보고서는 `aria-current="page"`로 현재 메뉴를 알리는 것과 `role="search"` 양식을 웹 표준 지식으로 판단했다고 적었습니다. 두 처리 모두 off 화면에 있던 것입니다. [WAI-ARIA 1.2 aria-current](https://www.w3.org/TR/wai-aria-1.2/#aria-current), [WAI-ARIA 1.2 search 역할](https://www.w3.org/TR/wai-aria-1.2/#search)
- 명도 대비 값은 개발 에이전트가 WCAG 상대 휘도 공식을 손으로 계산한 것입니다. [WCAG 2.2 상대 휘도](https://www.w3.org/TR/WCAG22/#dfn-relative-luminance)

## 검증 결과

Playwright 1.66 스크립트가 실행한 헤드리스 Chrome 158.0.8127.37(창 크기 1280×900)에 KWCAG 검사 0.1.17 확장의 검사 스크립트(axe-core 4.14.1 포함)를 확장과 같은 순서로 주입해 검사했습니다. 확장의 사이드 패널 화면은 쓰지 않았습니다. 마크업은 확장의 마크업 검사와 같은 html-validate 10.17.1 규칙으로 검사했습니다. 마우스와 키보드 조작은 사람이 아니라 스크립트가 보냈습니다. 규칙 수는 ‘위반 / 판정 보류 / 통과’ 순서이고, 요소 수가 아니라 규칙 종류 수입니다. KWCAG 검사 0.1.17은 건너뛰기 링크가 예상 Tab 순서의 첫 항목이고 연결 대상이 있으면 통과로 처리합니다(0.1.16은 판정 보류로 남겼습니다).

### 브라우저에서 관찰한 결과

- off에서 판정 보류였던 color-contrast(메뉴 링크 9개)가 on에서는 위반이나 판정 보류로 나오지 않았습니다. 통과 규칙은 28개에서 29개로 늘었습니다.
- 두 화면 모두 건너뛰기 링크와 관련해 위반이나 판정 보류로 나온 규칙은 없었습니다.
- 두 화면 모두 첫 Tab에서 ‘본문 바로가기’가 초점을 받았고 화면에 보였습니다.
- ‘본문 바로가기’에서 Enter를 누르면 두 화면 모두 주소가 `#main`으로 바뀌었습니다. 그때 초점을 가진 요소(`document.activeElement`)는 off에서 `body`, on에서 `main`이었습니다. 이어서 Tab을 한 번 누른 뒤에는 두 화면 모두 `body`였습니다.
- Tab 순서는 두 화면이 같았습니다. ‘본문 바로가기’, 로고 ‘푸른숲도서관’, 검색 입력란, 검색 버튼, 메뉴 10개였고 그다음은 `body`였습니다. 초점 표시가 없는 정지점은 없었습니다.
- 두 화면 모두 메뉴 영역의 링크는 10개이고 영역 이름은 ‘주 메뉴’였습니다. `aria-current`가 붙은 항목은 ‘이용 안내’였습니다.
- 두 화면 모두 검색 입력란의 레이블과 안내 문구는 ‘검색어 입력’이었습니다. 레이블은 화면에 보이지 않았습니다.
- 폭 320px에서 가로 넘침은 두 화면 모두 0px이었습니다.

### 코드에서 확인한 사실

- off와 on의 차이는 네 곳입니다. `index.html`에서는 `<main id="main">`에 `tabindex="-1"`이 붙었습니다. `style.css`에서는 메뉴 글자색이 `#8a8a8a`에서 `#666`으로, 검색 양식 테두리가 `#999`에서 `#767676`으로 바뀌었고 `main:focus { outline: none; }`이 추가됐습니다.
- 흰 배경(`#fff`)과의 대비를 WCAG 상대 휘도 공식으로 계산하면 `#8a8a8a`는 3.45:1, `#666`은 5.74:1, `#767676`은 4.54:1입니다. 보고서의 값과 같습니다. 현재 메뉴의 `#1b6b35`는 6.56:1입니다.
- on에서 건너뛰기 링크로 초점을 받은 `main`에는 초점 테두리를 그리지 않습니다(`main:focus { outline: none; }`). `main`은 Tab 정지점이 아닙니다.
- `main`과 푸터 안에는 두 화면 모두 초점을 받는 요소가 없습니다.
- ‘본문 바로가기’ 링크, 화면에서 숨긴 레이블, 안내 문구 색(`#6b6b6b`), 검색 버튼 크기(`width: 44px; height: 40px`), 메뉴 링크의 안쪽 여백(`8px 10px`)은 off와 같습니다.
- 검색 양식은 두 화면 모두 `onsubmit="return false"`입니다. 화면에 JavaScript 파일은 없습니다.

## 미검증 항목

on 보고서가 ‘브라우저에서 확인할 동작’으로 남긴 항목 가운데 아래는 브라우저 기록이 없습니다.

- ‘본문 바로가기’ 실행 뒤 다음 Tab이 본문에서 이어지는지는 이 기록으로 판단할 수 없습니다. 기록은 Tab을 누른 뒤 초점을 가진 요소가 `body`였다는 값뿐이고, 본문과 푸터에 초점을 받는 요소가 없기 때문입니다.
- 메뉴와 검색 버튼의 초점 테두리가 3px 초록색으로 보이는지는 확인하지 않았습니다. 기록은 초점 표시가 있는지뿐입니다.
- 폭 320px에서 메뉴가 줄바꿈되는 모양은 확인하지 않았습니다. 기록은 가로 넘침 값뿐입니다.
- 스크린 리더 발화: 검색 입력란을 ‘검색어 입력’으로, 버튼을 ‘검색’으로 읽는지와 현재 메뉴를 현재 페이지로 읽는지 확인하지 않았습니다.
- 검색 양식을 제출했을 때 아무 일이 없는지는 브라우저에서 확인하지 않았습니다.

그 밖의 미검증 항목입니다.

- 바뀐 메뉴 글자의 측정 대비 값은 기록에 없습니다. 확장 검사 기록에는 위반과 판정 보류 요소의 대비만 남습니다.
- ‘본문 바로가기’ 실행 뒤 스크린 리더가 읽는 위치는 확인하지 않았습니다.
- 실제 터치 기기, Chrome 이외의 브라우저, 화면 확대 상태는 확인하지 않았습니다.
