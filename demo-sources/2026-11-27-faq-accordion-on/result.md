# 자주 묻는 질문 · 접근성 자료 적용 (on) 실행 결과

푸른숲도서관 자주 묻는 질문 화면을 국내 접근성 자료(KWCAG 2.2, NIA 제작기법)에 맞춰 개선한 결과입니다. [기본 개발 (off)](/?demo=2026-11-27-faq-accordion-off) 화면을 복사한 뒤, 자료를 조회해 적용하는 개발 절차를 켜고 같은 요청서 기준으로 고쳤습니다.

확장 검사에서 off에 남아 있던 `color-contrast` 판정 보류가 사라져, 두 상태 모두 위반과 판정 보류가 0이 됐습니다. 바꾼 곳은 `style.css`의 ‘Q’, ‘A’ 글자색 두 줄뿐입니다. on 개발 에이전트는 나머지 요구사항을 off의 구현이 이미 충족한다고 보고했습니다. 펼침 동작과 Tab 순서는 off와 같았습니다.

## 사용 방법

- 질문 줄을 누르면 답이 펼쳐지고, 다시 누르면 접힙니다. 키보드로는 Tab으로 질문에 초점을 두고 Enter나 Space를 누릅니다.
- 여러 질문을 동시에 펼칠 수 있습니다.
- 답 끝의 ‘바로가기’ 링크는 요청서대로 주소가 `#`이고, 눌러도 페이지가 이동하지 않습니다.
- off 화면과 나란히 열어 ‘Q’, ‘A’ 글자색을 비교합니다.

## 요청서와 조정한 부분

개발 에이전트에게 준 ‘화면 요청서: 자주 묻는 질문’의 전문입니다.

> ### 공통 사항
>
> 가상의 기관 ‘푸른숲도서관’(전시 일정은 ‘푸른숲미술관’)의 화면입니다. HTML, CSS, JavaScript만 쓰고 외부 라이브러리와 CDN은 쓰지 않습니다. 모든 파일은 지정한 데모 폴더 안에 두고, 진입 페이지는 `index.html`입니다. 페이지 제목은 `<화면 이름> - 한국 웹 접근성 플레이그라운드`, 설명(meta description)은 요청서에 적은 문장을 씁니다. 데스크톱과 폭 320px 화면에서 모두 쓸 수 있어야 합니다. 결과 문서는 다른 담당자가 쓰므로 만들지 않습니다.
>
> ### 요청 내용
>
> 설명: 질문을 눌러 답을 펼치고 안내 페이지로 이동합니다.
>
> 질문 다섯 개(회원증 발급, 대출 권수와 기간, 연체, 열람실 예약, 분실 도서)와 답을 보여 줍니다. 질문을 누르면 답이 펼쳐지고 다시 누르면 접힙니다. 여러 개를 동시에 펼쳐도 됩니다. 답마다 관련 안내 페이지 링크가 하나씩 있습니다(주소는 `#`).
>
> 디자인 시안: 질문 줄 전체가 누르는 영역이고 오른쪽 끝에 +/− 아이콘이 있습니다(펼치면 −). 답 안의 링크는 문장 끝의 ‘바로가기’입니다. 질문 앞 ‘Q’는 연한 초록 `#9ccc9c` 굵은 글씨, 답 앞 ‘A’는 `#cccccc`입니다.

요청서 시안과 다르게 구현한 부분은 두 가지입니다. 근거 구분과 대비 값은 on 개발 에이전트의 보고를 따랐습니다.

| 요청서 시안 | 조정한 내용 | 이유 |
| --- | --- | --- |
| 질문 앞 ‘Q’ 연한 초록 `#9ccc9c` 굵은 글씨 | 같은 초록 계열의 `#2f6b3a`로 바꿨습니다. 굵은 글씨는 그대로입니다. | 시안 색은 흰 배경에서 약 1.9:1이고, 16px 굵은 글씨에는 4.5:1 이상이 필요하다고 보고했습니다(5.4.3, KWCAG 요구사항). 바꾼 색은 약 6:1이라고 보고했습니다. |
| 답 앞 ‘A’ `#cccccc` | `#595959`로 바꿨습니다. | 시안 색은 답 배경 `#f7f7f7`에서 약 1.5:1이라고 보고했습니다(5.4.3, KWCAG 요구사항). 바꾼 색은 약 6.5:1이라고 보고했습니다. |

개발 에이전트는 대비 값이 스크립트 실행이 승인되지 않아 상대 휘도 공식으로 직접 계산한 근사값이라고 적었습니다. 확장 검사가 off에서 측정한 ‘Q’ 글자의 대비는 1.82:1입니다.

질문 줄 전체를 누르는 영역, 오른쪽 끝의 +/− 아이콘, 문장 끝의 ‘바로가기’ 링크는 시안대로입니다. 페이지 제목, 설명, `lang="ko"`도 그대로 두었습니다. `index.html`과 `script.js`는 바꾸지 않았습니다. 개발 에이전트는 접근성과 무관한 기능 결함을 찾지 못했다고 보고했습니다. 실제 안내 페이지가 생기면 링크 주소 `#`를 해당 주소로 바꿔야 한다는 제안을 적었고, 구현하지는 않았습니다.

## 개발 조건

- 모델과 실행 도구: off와 같은 Claude Sonnet 5.5, Claude Code 2.1.332(헤드리스 실행)
- 실행 위치: 이 저장소 밖의 빈 폴더입니다. 그래서 이 저장소의 프로젝트 지침은 읽지 않았습니다.
- 개발 절차: off 화면을 복사한 폴더에서 국내 접근성 자료를 조회해 적용하는 절차를 켰습니다.
- 지시: 같은 요청서 기준으로 화면을 개선하게 했습니다. 요청서 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 요청자가 미리 승인했습니다. 질문하지 말고 개선까지 마치게 했습니다.
- 자료 조회: 설정 확인, 절차 문서, 자료 목록, 레코드 순서로 읽었습니다. 자료 조회 명령 19회는 모두 주소 하나에 명령 하나인 같은 형태였고 실패는 없었습니다. KWCAG 레코드 14개와 NIA 사례 레코드 4개를 읽었습니다. 화면 종류와 관계없이 고르는 12개 항목(5.3.2, 5.4.1, 5.4.3, 5.4.4, 6.1.1, 6.1.2, 6.1.3, 6.4.2, 6.5.3, 7.1.1, 7.2.1, 8.1.1)의 레코드는 모두 받았습니다.
- 도구: 브라우저 도구와 MCP 서버가 없었고, 디자인 검사 플러그인을 껐습니다. 그래서 개발 에이전트는 코드와 명령으로만 확인했습니다.
- 셸 명령: 허용한 명령은 `node`, `ls`, `cat`, `curl`, `mkdir`, `cp`입니다. 그 밖의 명령과 일부 복합 명령은 거부됐습니다. 이 세션에서 거부된 호출은 3건으로, 모두 명도 대비를 계산하는 `python3` 스크립트를 만들거나 실행하려던 명령이었습니다. 그래서 개발 에이전트는 대비를 손으로 계산했습니다.
- 수정 요청: 이 화면에서 기능 결함을 찾지 못해 수정 요청을 보내지 않았습니다.
- 보존: on 개발 뒤에도 off 화면의 파일이 바뀌지 않았음을 해시로 확인했습니다.
- 재실행: 이 문서는 세 번째 실행의 결과입니다. 첫 실행에서는 다른 모델(Claude Opus 5.5)로 이 저장소 안에서 off 화면 13개를 만들었습니다. 13개 모두 확장 검사 위반이 0건이었고, 개발 에이전트들은 이 저장소의 프로젝트 지침과 일반 지식에 따라 시안을 접근성 기준에 맞춰 바꿨다고 보고했습니다. 첫 실행에서는 on 화면을 만들지 않았습니다. 두 번째 실행(2026-11-27 오후)에서는 모델과 실행 위치를 바꿔 다시 만들었습니다. 이때 off 개발 에이전트 13개 중 12개가 절차의 설정을 읽는 명령에서 자료 목록(검사항목 33개의 제목과 주소)을 함께 받았습니다. on 개발 에이전트 13개는 모두 일괄 내려받기 명령이 거부됐고, 일부는 필수 항목의 본문을 끝까지 읽지 못했습니다. 세 번째 실행(2026-11-27 밤)에서는 개발 절차를 설정 확인 문서와 절차 문서로 나눠 off 세션이 절차와 자료를 보지 않게 했고, 자료 조회 명령을 한 형태로 고정했습니다. 요청서는 두 번째 실행과 같은 확정본이고, 화면은 처음부터 다시 만들었습니다.

### 자료 밖 근거

- 펼침 구조: `aria-expanded`, `aria-controls`를 쓰는 아코디언 패턴과 답 영역의 `hidden` 속성은 WAI-ARIA와 HTML 표준 지식에 근거합니다. off에 이미 있었고 이번에 바꾸지 않았습니다. [aria-expanded](https://www.w3.org/TR/wai-aria-1.2/#aria-expanded) · [aria-controls](https://www.w3.org/TR/wai-aria-1.2/#aria-controls) · [HTML hidden 속성](https://html.spec.whatwg.org/multipage/interaction.html#the-hidden-attribute)
- 개발 에이전트는 이 구현이 W3C ARIA Authoring Practices Guide의 [아코디언 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/accordion/)과 같은 형태라고 적었습니다. 그 문서 자체는 읽지 않았다고 보고했습니다.

## 검증 결과

Playwright 1.66 스크립트가 실행한 헤드리스 Chrome 158.0.8127.37(창 크기 1280×900)에 KWCAG 검사 0.1.17 확장의 검사 스크립트(axe-core 4.14.1 포함)를 확장과 같은 순서로 주입해 검사했습니다. 확장의 사이드 패널 화면은 쓰지 않았습니다. 마크업은 확장의 마크업 검사와 같은 html-validate 10.17.1 규칙으로 검사했습니다. 마우스와 키보드 조작은 사람이 아니라 스크립트가 보냈습니다. 규칙 수는 ‘위반 / 판정 보류 / 통과’ 순서이고, 요소 수가 아니라 규칙 종류 수입니다.

| 320px 가로 스크롤 | 없음 | 없음 |

| 콘솔 오류(초기 상태) | 0건 | 0건 |

### 브라우저에서 관찰한 결과

- on에서는 off의 `color-contrast` 판정 보류가 사라지고 통과 규칙이 하나씩 늘었습니다. 초기 상태는 19개에서 20개로, 첫 질문을 펼친 상태는 24개에서 25개로 늘었습니다.
- ‘Q’ 글자의 계산된 색은 off가 `rgb(156, 204, 156)`, on이 `rgb(47, 107, 58)`이었습니다.
- 두 화면 모두 첫 질문을 클릭하면 `aria-expanded`가 `true`가 되고 답 영역 하나가 보였습니다. 다시 클릭하면 `false`가 됐습니다.
- 두 화면 모두 Enter를 누르면 `aria-expanded`가 `true`가 됐고, 이어서 Space를 누르면 `false`가 됐습니다. 초점은 그 질문 버튼에 남아 있었습니다.
- 두 화면 모두 첫 번째와 두 번째 질문을 차례로 클릭하면 두 질문이 함께 펼쳐진 상태가 됐습니다.
- 모두 접힌 상태의 Tab 순서는 두 화면 모두 질문 버튼 다섯 개였고, 그다음은 `body`였습니다. 초점을 받은 요소마다 초점 표시가 있었습니다.
- 첫 질문을 펼친 상태에서 ‘바로가기’ 링크의 크기는 두 화면 모두 55×18px이었습니다.

### 코드에서 확인한 사실

- off와 on의 차이는 `style.css`의 두 줄입니다. 질문 앞 ‘Q’의 색이 `#9ccc9c`에서 `#2f6b3a`로, 답 앞 ‘A’의 색이 `#ccc`에서 `#595959`로 바뀌었습니다.
- `index.html`과 `script.js`는 두 화면이 같습니다.
- ‘Q’, ‘A’ 글자는 두 화면 모두 `aria-hidden="true"`입니다.
- ‘바로가기’ 링크의 크기와 모양을 정하는 CSS는 두 화면이 같습니다.

## 미검증 항목

- ‘바로가기’ 링크를 눌렀을 때 페이지가 이동하지 않는지는 코드로만 확인했습니다.
- 스크린 리더 발화: 질문을 확장·축소 상태와 함께 읽는지, 링크를 ‘바로가기: …’로 읽는지 확인하지 않았습니다.
- 실제 터치 기기와 Chrome 이외의 브라우저에서는 확인하지 않았습니다.
- 바뀐 ‘Q’, ‘A’ 색의 대비를 측정한 값은 기록에 없습니다. 확장 검사에서 `color-contrast`가 위반과 판정 보류에 나오지 않은 것만 확인했습니다. 개발 에이전트의 대비 값은 손으로 계산한 근사값입니다.
- 답을 펼친 상태에서 Tab이 ‘바로가기’ 링크로 이동하는지, 그때 초점 윤곽선이 보이는지 기록하지 않았습니다.
- 폭 320px에서는 가로 스크롤만 확인했습니다. 글이 잘리지 않는지와 화면 200% 확대는 확인하지 않았습니다.
