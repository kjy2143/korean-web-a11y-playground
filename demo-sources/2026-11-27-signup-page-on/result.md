# 회원가입 · 접근성 자료 적용 (on) 실행 결과

푸른숲도서관 회원가입 화면을 국내 접근성 자료(KWCAG 2.2, NIA 제작기법)에 맞춰 개선한 결과입니다. [기본 개발 (off)](/?demo=2026-11-27-signup-page-off) 화면을 복사한 뒤, 자료를 조회해 적용하는 개발 절차를 켜고 같은 요청서 기준으로 고쳤습니다.

확장 검사에서 off의 명도 대비 위반(보조 안내 글씨 2.16:1)이 사라졌습니다. 빈 값으로 제출한 상태의 조작 대상 크기 위반(오류 요약 링크 네 개)은 on 개발 직후에도 남아 있었습니다. 같은 개발 세션에 한 번 보고해 수정본을 받았고, 수정 뒤에는 두 상태 모두 위반과 판정 보류가 0건이었습니다. 레이블에는 ‘필수’ 글자가 보이게 됐고, 제출 오류가 나면 초점이 오류 요약이 아니라 첫 오류 입력란으로 갑니다.

## 사용 방법

- 아이디(영문 소문자·숫자 4~12자), 비밀번호(8자 이상), 비밀번호 확인, 이메일을 입력합니다.
- ‘[필수] 이용약관 동의’와 ‘[필수] 개인정보 수집·이용 동의’를 선택합니다. ‘전체 동의’를 누르면 약관 세 개가 함께 선택됩니다.
- ‘가입하기’를 누르면 입력값을 검사합니다. 틀린 항목이 있으면 화면 위쪽에 오류 요약이 나타나고 각 입력란 아래에 오류 문구가 표시됩니다. 초점은 첫 오류 입력란으로 갑니다.
- 모두 맞으면 같은 페이지가 가입 완료 화면으로 바뀝니다. 서버로 보내는 값은 없습니다.
- off 화면과 나란히 열어 보조 안내 글씨의 색, 레이블의 ‘필수’ 글자, 빈 값으로 제출한 뒤의 초점 위치를 비교합니다.

## 요청서와 조정한 부분

개발 에이전트에게 준 ‘화면 요청서: 회원가입’의 전문입니다.

> ### 공통 사항
>
> 가상의 기관 ‘푸른숲도서관’(전시 일정은 ‘푸른숲미술관’)의 화면입니다. HTML, CSS, JavaScript만 쓰고 외부 라이브러리와 CDN은 쓰지 않습니다. 모든 파일은 지정한 데모 폴더 안에 두고, 진입 페이지는 `index.html`입니다. 페이지 제목은 `<화면 이름> - 한국 웹 접근성 플레이그라운드`, 설명(meta description)은 요청서에 적은 문장을 씁니다. 데스크톱과 폭 320px 화면에서 모두 쓸 수 있어야 합니다. 결과 문서는 다른 담당자가 쓰므로 만들지 않습니다.
>
> ### 요청 내용
>
> 설명: 입력 오류를 고치고 필수 약관에 동의해 가입을 완료합니다.
>
> 아이디(영문 소문자·숫자 4~12자), 비밀번호(8자 이상), 비밀번호 확인, 이메일을 입력받습니다. 약관은 ‘[필수] 이용약관 동의’, ‘[필수] 개인정보 수집·이용 동의’, ‘[선택] 소식 메일 받기’와 ‘전체 동의’입니다. ‘가입하기’를 누르면 입력값을 검사해 틀린 항목을 알려 주고, 모두 맞으면 같은 페이지를 가입 완료 화면으로 바꿉니다.
>
> 디자인 시안: 입력란 위에 제목 없이 안내 문구만 표시합니다(예: ‘아이디 (영문 소문자·숫자 4~12자)’). 필수 입력란은 오른쪽 위에 작은 빨간 점을 찍습니다. 약관 동의는 디자인한 원형 체크 아이콘을 쓰고 기본 체크박스 모양은 보이지 않게 합니다. 입력 규칙 같은 보조 안내 글씨는 `#b0b0b0`입니다. 오류가 나면 입력란 테두리를 빨간색으로 바꿉니다.

개발 에이전트는 시안 네 가지를 KWCAG 요구사항과 견주어 아래처럼 정리했습니다. 근거 구분은 on 개발 에이전트의 보고를 따랐고, 표의 항목은 모두 KWCAG 요구사항입니다. 코드를 바꾼 것은 앞의 두 가지입니다.

| 요청서 시안 | 조정한 내용 | 보고서가 든 근거 |
| --- | --- | --- |
| 보조 안내 글씨 `#b0b0b0` | `#6b6b6b`로 바꿨습니다. 보고서는 흰 배경 대비가 2.17:1에서 5.33:1로 올라간다고 적었습니다. | 5.4.3(4.5:1 이상) |
| 필수 표시는 빨간 점만 | 빨간 점은 유지하고 레이블에 ‘필수’ 글자를 눈에 보이게 넣었습니다. off는 이 글자를 화면에서 숨겼습니다. | 5.4.1, 7.3.1 |
| 오류 표시는 빨간 테두리 | 테두리는 유지하고 오류 문구와 ‘⚠’ 기호를 함께 둡니다. off가 이미 갖춘 구현이라 바꾸지 않았습니다. | 5.4.1, 7.3.1 |
| 원형 체크 아이콘, 기본 체크박스 모양 숨김 | 시안대로 유지했습니다. 실제 `input`은 투명하게 두어 키보드 초점과 읽기가 그대로 동작하고, 초점은 아이콘에 표시된다고 보고서가 적었습니다. | 6.1.1, 6.1.2 |

입력란 위에 안내 문구만 두는 시안은 안내 문구가 `label`로 연결돼 있어 그대로 두었습니다.

시안과 충돌하지 않는 접근성 개선은 두 가지입니다.

- 제출 오류가 나면 초점을 오류 요약이 아니라 첫 오류 입력란으로 옮깁니다. 보고서는 입력란의 `aria-describedby`로 오류 문구가 함께 읽힌다고 적었습니다.
- 오류 요약의 `role="alert"`를 없애고, 오류 건수는 화면에서 숨긴 `role="status"` 영역에 알립니다. 보고서는 이중 낭독을 피하려는 조정이라고 적었습니다.

접근성과 무관한 기능 결함 수정도 하나 있습니다. off는 입력란의 오류가 한 번 표시되면 값을 고쳐도 오류 문구와 빨간 테두리가 다음 제출 때까지 남았고, 오류 요약은 어느 항목을 고쳐도 그대로였습니다. 필수 약관은 선택하면 그 약관의 오류 문구만 지워졌습니다. 이 off 동작은 코드로 확인한 것입니다. on은 오류가 표시된 항목을 입력하거나 체크하는 즉시 다시 검사해 문구를 지우고 요약을 갱신합니다. 비밀번호를 고치면 비밀번호 확인도 다시 검사합니다.

개발 에이전트는 아이디와 이메일에 입력란을 벗어날 때 바로 검사하는 기능을 제안만 하고 넣지 않았습니다. 요청에 없는 기능이라는 이유입니다.

### 검증 뒤 결함 보고와 수정

- 보고 전: on 화면을 검사하니 빈 값으로 제출한 상태에서 오류 요약의 링크 네 개가 조작 대상 크기 위반(target-size)이었습니다. 요약 링크 여섯 개는 모두 높이가 19px이었습니다(폭 143~217px).
- 보고: 같은 개발 세션에 관찰한 현상만 한 번 전했습니다. 링크 높이와 폭, 검사 도구가 표시한 링크 네 개, 초기 상태에는 표시된 항목이 없다는 점입니다. 고칠지 여부는 개발 에이전트가 판단하게 했습니다.
- 개발 에이전트의 답: `style.css`의 `.summary a` 규칙에 `display:inline-block;min-height:32px;padding:4px 0;line-height:24px`를 더했습니다. 링크가 인라인 요소라 높이가 글자 줄 높이에 그친 것이 원인이라고 답했습니다. 근거로는 6.1.3(조작 가능)과 그 크기 기준을 든 NIA 기본 규칙(권장 사항, 모바일에서 24×24px 이상)을 들었습니다. 링크 여섯 개 중 네 개만 표시된 이유는 확인하지 못했고, 브라우저에서 다시 확인하지도 못했다고 보고했습니다.
- 수정 후: 요약 링크 여섯 개의 높이가 모두 32px이 됐고, 빈 값 제출 상태의 확장 검사 결과가 1 / 0 / 28에서 0 / 0 / 29로 바뀌었습니다.

## 개발 조건

- 모델과 실행 도구: off와 같은 Claude Sonnet 5.5, Claude Code 2.1.332(헤드리스 실행). 개발 세션은 대화 턴 43회, 126초였습니다.
- 실행 위치: 이 저장소 밖의 빈 폴더입니다. 그래서 이 저장소의 프로젝트 지침은 읽지 않았습니다.
- 개발 절차: off 화면을 복사한 폴더에서 국내 접근성 자료를 조회해 적용하는 절차를 켰습니다.
- 지시: 같은 요청서 기준으로 화면을 개선하게 했습니다. 요청서 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 요청자가 미리 승인했습니다. 질문하지 말고 개선까지 마치게 했습니다.
- 자료 조회: 설정 확인, 절차 문서, 자료 목록, 레코드 순서로 읽었습니다. 자료 조회 명령 22회는 모두 주소 하나에 명령 하나인 같은 형태였고, 실패한 조회는 없었습니다. KWCAG 레코드 17개와 NIA 사례 레코드 4개를 읽었습니다. 화면 종류와 관계없이 고르는 12개 항목(5.3.2, 5.4.1, 5.4.3, 5.4.4, 6.1.1, 6.1.2, 6.1.3, 6.4.2, 6.5.3, 7.1.1, 7.2.1, 8.1.1)의 레코드를 모두 받았습니다.
- 도구: 브라우저 도구와 MCP 서버가 없었고, 디자인 검사 플러그인을 껐습니다. 그래서 개발 에이전트는 코드와 명령으로만 확인했습니다. 허용한 셸 명령은 `node`, `ls`, `cat`, `curl`, `mkdir`, `cp`입니다. `node` 명령 1건이 거부됐습니다. 보고서에 이 거부 때문에 하지 못했다고 적은 작업은 없습니다.
- 수정 요청: 검증에서 찾은 현상을 같은 개발 세션에 한 번 보고했고 수정본을 받았습니다. 내용은 위 ‘검증 뒤 결함 보고와 수정’에 적었습니다.
- 보존: on 개발과 on 결함 수정 뒤에도 off 화면의 파일이 바뀌지 않았음을 해시로 확인했습니다.
- 재실행: 이 문서는 세 번째 실행의 결과입니다.
  1. 첫 실행에서는 다른 모델(Claude Opus 5.5)로 이 저장소 안에서 off 화면 13개를 만들었습니다. 13개 모두 확장 검사 위반이 0건이었고, 개발 에이전트들은 이 저장소의 프로젝트 지침과 일반 지식에 따라 시안을 접근성 기준에 맞춰 바꿨다고 보고했습니다. on 화면은 만들지 않았습니다.
  2. 두 번째 실행(2026-11-27 오후)에서는 모델과 실행 위치를 바꿔 다시 만들었습니다. off 개발 에이전트 13개 중 12개가 절차의 설정을 읽는 명령에서 자료 목록(검사항목 33개의 제목과 주소)을 함께 받았습니다. on 13개는 모두 일괄 내려받기 명령이 거부됐고, 일부는 필수 항목의 본문을 끝까지 읽지 못했습니다.
  3. 세 번째 실행(2026-11-27 밤)에서는 개발 절차를 설정 확인 문서와 절차 문서로 나눠 off 세션이 절차와 자료를 보지 않게 했고, 자료 조회 명령을 한 형태로 고정했습니다. 요청서는 두 번째 실행과 같은 확정본이고, 화면은 처음부터 다시 만들었습니다.

## 검증 결과

Playwright 1.66 스크립트가 실행한 헤드리스 Chrome 158.0.8127.37(창 크기 1280×900)에 KWCAG 검사 0.1.17 확장의 검사 스크립트(axe-core 4.14.1 포함)를 확장과 같은 순서로 주입해 검사했습니다. 확장의 사이드 패널 화면은 쓰지 않았습니다. 마크업은 확장의 마크업 검사와 같은 html-validate 10.17.1 규칙으로 검사했습니다. 마우스와 키보드 조작은 사람이 아니라 스크립트가 보냈습니다. 규칙 수는 ‘위반 / 판정 보류 / 통과’ 순서이고, 요소 수가 아니라 규칙 종류 수입니다. KWCAG 검사 0.1.17은 건너뛰기 링크가 예상 Tab 순서의 첫 항목이고 연결 대상이 있으면 통과로 처리합니다(0.1.16은 판정 보류로 남겼습니다).

on 열의 값은 결함 수정 뒤의 값입니다. 수정 전 값이 다른 항목에는 괄호로 함께 적었습니다.

| --- | --- | --- |
| 확장 검사: 초기 상태 | 1 / 0 / 23 | 0 / 0 / 27 |

### 브라우저에서 관찰한 결과

- on에서는 초기 상태와 빈 값 제출 상태 모두 위반과 판정 보류가 없었습니다. 수정 전에는 빈 값 제출 상태에서 `#userid`, `#pw`, `#email`, `#agree-terms`로 가는 요약 링크 네 개가 target-size 위반이었습니다.
- 빈 값으로 ‘가입하기’를 누르면 두 화면 모두 `aria-invalid`가 붙은 요소가 6개였고, 요약에는 ‘입력 내용을 확인해 주세요. (6건)’과 항목별 문구 여섯 개가 표시됐습니다. 초점은 off에서 오류 요약으로, on에서 아이디 입력란으로 갔습니다.
- 두 화면 모두 입력란의 이름은 ‘아이디 (영문 소문자·숫자 4~12자) 필수’처럼 ‘필수’를 포함했습니다. off에서는 이 글자가 숨김 클래스(`vh`) 요소에, on에서는 `class="req"` 요소에 들어 있었습니다.
- ‘전체 동의’에 초점을 두고 Space를 누르면 두 화면 모두 체크 상자 네 개가 선택됐습니다. off에서 기록된 `TypeError`는 on에서 수정 전과 수정 후 모두 기록되지 않았습니다.
- 올바른 값을 넣고 ‘가입하기’를 누르면 두 화면 모두 ‘가입이 완료되었습니다’가 표시됐고 초점이 그 제목으로 갔습니다.
- 두 화면 모두 Tab 순서가 같았고, 초점 표시가 없는 정지점은 없었습니다.

### 코드에서 확인한 사실

- `style.css`: 보조 안내 글씨 변수가 `--hint:#6b6b6b`로 바뀌었습니다. ‘필수’ 글자는 `.req{color:#b00020;font-size:.8rem;font-weight:700}`입니다. `.summary a`에는 `display:inline-block;min-height:32px;padding:4px 0;line-height:24px`가 있습니다. 초점 윤곽선 규칙의 대상이 요약 영역(`.summary`)에서 요약 안의 링크(`.summary a`)로 바뀌었습니다.
- `index.html`: 화면에서 숨긴 `<p id="status" role="status">`가 추가됐고, 오류 요약에서 `role="alert"`와 `tabindex="-1"`이 빠졌습니다. 레이블 네 곳의 ‘필수’가 숨김 요소에서 `class="req"` 요소로 바뀌었습니다. `id`는 23개이고 중복이 없습니다.
- `script.js`: 제출 때 오류가 있으면 상태 영역에 ‘입력 내용을 확인해 주세요. N건의 오류가 있습니다.’를 넣고 첫 오류 입력란에 초점을 둡니다. 오류가 표시된 입력란은 `input` 이벤트에서 다시 검사하고 요약을 다시 만듭니다.
- off의 `TypeError`를 일으킨 코드는 on에 남아 있지 않습니다. ‘전체 동의’와 개별 약관의 처리가 필수 약관 두 개만 다시 검사하도록 바뀌어, 오류 문구 요소가 없는 ‘소식 메일 받기’에는 접근하지 않습니다. 개발 보고서는 이 오류를 따로 적지 않았습니다.
- 빨간 점, 원형 체크 아이콘, ‘본문 바로가기’, 가입 완료 화면의 마크업은 off와 같습니다.
- 대비 값 5.33:1(보조 안내), 7.33:1(‘필수’ 글자), 5.67:1(오류색), 4.54:1(입력란 테두리), 6.42:1(버튼의 흰 글자)은 보고서가 계산한 값입니다.

## 미검증 항목

- 스크린 리더 발화: 아이디 입력란에서 레이블, ‘필수’, 오류 문구를 함께 읽는지와 오류 건수 안내가 겹치지 않는지 확인하지 않았습니다.
- 오류가 난 뒤 값을 고치면 해당 오류 문구와 요약 항목이 바로 사라지는지, 비밀번호를 고치면 비밀번호 확인 오류가 갱신되는지는 코드로만 확인했습니다.
- 빈 값 제출 뒤 ‘⚠’ 문구와 빨간 테두리가 화면에 어떻게 보이는지는 따로 기록하지 않았습니다. 초점 위치와 `aria-invalid` 개수만 기록했습니다.
- ‘전체 동의’를 끄는 동작과 개별 약관을 눌렀을 때 ‘전체 동의’가 바뀌는 동작은 브라우저에서 확인하지 않았습니다.
- 오류 요약의 링크를 클릭하거나 Enter로 눌렀을 때 해당 입력란으로 초점이 가는지 확인하지 않았습니다. 링크에 초점을 두었을 때 윤곽선이 잘리지 않는지도 확인하지 않았습니다.
- 가입 완료 뒤 페이지 제목이 ‘가입 완료’로 바뀌는지는 코드로만 확인했습니다. 완료 제목으로 초점이 가는 것은 브라우저에서 확인했습니다.
- 폭 320px에서는 초기 상태에 가로 스크롤이 없다는 것만 확인했습니다. 레이블, 안내, ‘필수’의 줄바꿈 모양과 오류 요약이 표시된 상태는 확인하지 않았습니다.
- ‘본문 바로가기’를 실행한 뒤의 초점 위치, 고대비 모드에서 체크 아이콘과 오류 표시가 보이는지, 화면 확대는 확인하지 않았습니다.
- 실제 터치 기기와 Chrome 이외의 브라우저에서는 확인하지 않았습니다.
