# 이용 안내 창 · 접근성 자료 적용 (on) 실행 결과

자동으로 열리는 ‘12월 이용 안내’ 창을 국내 접근성 자료(KWCAG 2.2, NIA 제작기법)에 맞춰 개선한 결과입니다. [기본 개발 (off)](/?demo=2026-11-27-modal-layer-off) 화면을 복사한 뒤, 자료를 조회해 적용하는 개발 절차를 켜고 같은 요청서 기준으로 고쳤습니다.

확장 검사에서 off의 창 열림 상태에 있던 `color-contrast` 위반 1개가 on에서 사라졌습니다. on 개발 에이전트는 ‘오늘 하루 보지 않기’ 글자색을 `#aaaaaa`에서 `#6b6b6b`로 바꾸고, 창의 HTML 위치를 본문 앞으로 옮기고, 창 바깥 누름을 취소할 수 있게 했습니다. 첫 검증에서 자동으로 열린 창을 닫으면 초점이 `body`에 남는 현상을 관찰해 같은 개발 세션에 한 번 보고했습니다. 수정본에서는 초점이 페이지 제목(`h1`)으로 갔습니다.

## 사용 방법

- 페이지에 들어오면 안내 창이 자동으로 열립니다.
- 창 오른쪽 위의 X 버튼, Esc 키, 창 바깥 누르기로 창을 닫습니다.
- ‘오늘 하루 보지 않기’를 선택하고 닫으면 그날은 창이 자동으로 열리지 않습니다.
- ‘이용 안내 보기’ 버튼으로 언제든 창을 다시 엽니다.
- off 화면과 나란히 열어 ‘오늘 하루 보지 않기’ 글자색과, 자동으로 열린 창을 닫은 뒤의 초점 위치를 비교합니다.

## 요청서와 조정한 부분

개발 에이전트에게 준 ‘화면 요청서: 이용 안내 창’의 전문입니다.

> ### 공통 사항
>
> 가상의 기관 ‘푸른숲도서관’(전시 일정은 ‘푸른숲미술관’)의 화면입니다. HTML, CSS, JavaScript만 쓰고 외부 라이브러리와 CDN은 쓰지 않습니다. 모든 파일은 지정한 데모 폴더 안에 두고, 진입 페이지는 `index.html`입니다. 페이지 제목은 `<화면 이름> - 한국 웹 접근성 플레이그라운드`, 설명(meta description)은 요청서에 적은 문장을 씁니다. 데스크톱과 폭 320px 화면에서 모두 쓸 수 있어야 합니다. 결과 문서는 다른 담당자가 쓰므로 만들지 않습니다.
>
> ### 요청 내용
>
> 설명: 안내 창을 열어 읽고 닫습니다.
>
> 도서관 소개 본문 두 문단과 ‘이용 안내 보기’ 버튼이 있는 페이지입니다. 페이지에 들어오면 ‘12월 이용 안내’ 창이 자동으로 열립니다. 창에는 제목, 안내 세 줄(연말 휴관, 대출 기간 연장, 무인 반납함 이용), ‘오늘 하루 보지 않기’ 체크, 닫기가 있습니다. ‘오늘 하루 보지 않기’를 체크하고 닫으면 그날은 자동으로 열리지 않습니다. ‘이용 안내 보기’ 버튼으로는 언제든 다시 엽니다.
>
> 디자인 시안: 닫기는 창 오른쪽 위의 X 아이콘만 둡니다. 뒤 화면은 반투명 검정으로 덮습니다. 창 바깥을 누르면 닫힙니다. ‘오늘 하루 보지 않기’ 글씨는 12px `#aaaaaa`입니다.

요청서 시안과 다르게 구현한 부분은 한 가지입니다.

| 요청서 시안 | 조정한 내용 | 이유 |
| --- | --- | --- |
| ‘오늘 하루 보지 않기’ 12px `#aaaaaa` | 12px은 두고 색을 `#6b6b6b`로 바꿨습니다. | `#aaaaaa`는 흰 배경에서 2.32:1이라 4.5:1에 못 미칩니다(5.4.3, KWCAG 요구사항). 개발 에이전트는 바꾼 색의 대비를 5.33:1로 계산했습니다. |

X 아이콘만 있는 닫기, 반투명 검정 배경, 창 바깥 누름으로 닫기, 페이지 진입 때 자동 열기는 시안대로 두었습니다. X 버튼은 `aria-label="닫기"`로 이름을 제공합니다. 개발 에이전트는 이 아이콘에 보이는 글자가 없어 6.5.3의 NIA 기본 규칙에 따라 검사 대상이 아니라고 판단했습니다. 자동 열기에 대해서는 7.2.1 본문이 레이어 팝업을 쓰지 않는 편이 바람직하다고 적고 있다고 보고했습니다. 그러나 새 창이 아니라 같은 페이지 안의 레이어이고 닫기와 다시 열기 수단이 있어 요청대로 유지했다고 적었습니다. 이 판단은 개발 에이전트가 내린 것입니다.

## 개발 조건

- 모델과 실행 도구: off와 같은 Claude Sonnet 5.5, Claude Code 2.1.332(헤드리스 실행)
- 실행 위치: 이 저장소 밖의 빈 폴더입니다. 그래서 이 저장소의 프로젝트 지침은 읽지 않았습니다.
- 개발 절차: off 화면을 복사한 폴더에서 국내 접근성 자료를 조회해 적용하는 절차를 켰습니다.
- 지시: 같은 요청서 기준으로 화면을 개선하게 했습니다. 요청서 시안이 KWCAG 요구사항과 충돌하면 요구사항을 우선하도록 요청자가 미리 승인했습니다. 질문하지 말고 개선까지 마치게 했습니다.
- 자료 조회: 설정 확인, 절차 문서, 자료 목록, 레코드 순서로 읽었습니다. 자료 조회 명령 21회는 모두 주소 하나에 명령 하나인 같은 형태였고 실패는 없었습니다. KWCAG 레코드 14개와 NIA 사례 레코드 6개를 읽었습니다. 화면 종류와 관계없이 고르는 12개 항목(5.3.2, 5.4.1, 5.4.3, 5.4.4, 6.1.1, 6.1.2, 6.1.3, 6.4.2, 6.5.3, 7.1.1, 7.2.1, 8.1.1)의 레코드는 모두 받았습니다.
- 도구: 브라우저 도구와 MCP 서버가 없었고, 디자인 검사 플러그인을 껐습니다. 그래서 개발 에이전트는 코드와 명령으로만 확인했습니다.
- 셸 명령: 허용한 명령은 `node`, `ls`, `cat`, `curl`, `mkdir`, `cp`입니다. 그 밖의 명령과 일부 복합 명령은 거부됐습니다. 이 세션에서 거부된 호출은 3건으로, `cat` 뒤에 다른 명령을 이은 복합 명령, `cp`와 `python3`을 이은 복합 명령, `python3` 명령이었습니다. 개발 에이전트는 명도 대비를 `node`로 계산했다고 보고했습니다.
- 수정 요청: 검증에서 관찰한 현상을 같은 on 개발 세션에 한 번 보고했습니다. 보고에는 재현 조작과 관찰 결과만 적었고, 고칠지는 개발 에이전트가 판단하게 했습니다. 수정 전후는 검증 결과에 적었습니다.
- 보존: on 개발과 on 결함 수정 뒤에도 off 화면의 파일이 바뀌지 않았음을 해시로 확인했습니다.
- 재실행: 이 문서는 세 번째 실행의 결과입니다. 첫 실행에서는 다른 모델(Claude Opus 5.5)로 이 저장소 안에서 off 화면 13개를 만들었습니다. 13개 모두 확장 검사 위반이 0건이었고, 개발 에이전트들은 이 저장소의 프로젝트 지침과 일반 지식에 따라 시안을 접근성 기준에 맞춰 바꿨다고 보고했습니다. 첫 실행에서는 on 화면을 만들지 않았습니다. 두 번째 실행(2026-11-27 오후)에서는 모델과 실행 위치를 바꿔 다시 만들었습니다. 이때 off 개발 에이전트 13개 중 12개가 절차의 설정을 읽는 명령에서 자료 목록(검사항목 33개의 제목과 주소)을 함께 받았습니다. on 개발 에이전트 13개는 모두 일괄 내려받기 명령이 거부됐고, 일부는 필수 항목의 본문을 끝까지 읽지 못했습니다. 세 번째 실행(2026-11-27 밤)에서는 개발 절차를 설정 확인 문서와 절차 문서로 나눠 off 세션이 절차와 자료를 보지 않게 했고, 자료 조회 명령을 한 형태로 고정했습니다. 요청서는 두 번째 실행과 같은 확정본이고, 화면은 처음부터 다시 만들었습니다.

### 자료 밖 근거

- 모달 창: 네이티브 `dialog`의 `showModal()`에 뒤 화면 비활성화, 첫 조작 요소 초점, Esc 처리를 맡겼습니다. [HTML dialog 요소](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element)
- 바깥 누름 취소: `pointerdown`과 `click`을 조합해 구현했습니다. 개발 에이전트는 6.5.2가 요구사항이지만 구현 방법은 자료에 없어 웹 표준 지식으로 구현했다고 적었습니다. [pointerdown 이벤트](https://www.w3.org/TR/pointerevents3/#the-pointerdown-event)
- 자동으로 열린 창을 닫은 뒤의 초점: `h1`에 `tabindex="-1"`을 주고 스크립트로 초점을 옮겼습니다. 개발 에이전트는 초점이 `body`에 남는 상태가 NIA 2.1.2 개선 필요 사례(권장 사항)의 내용과 어긋나지 않아 요구사항 위반으로 보지 않았다고 적었습니다. 고친 이유는 다음 Tab의 시작 위치와 화면낭독의 읽기 위치가 브라우저마다 달라질 수 있다는 자신의 판단이라고 적었습니다. `tabindex="0"`은 조작 요소가 아닌 글자가 Tab 순서에 들어가게 되므로 쓰지 않았다고 적었습니다. [HTML tabindex 속성](https://html.spec.whatwg.org/multipage/interaction.html#attr-tabindex)

## 검증 결과

Playwright 1.66 스크립트가 실행한 헤드리스 Chrome 158.0.8127.37(창 크기 1280×900)에 KWCAG 검사 0.1.17 확장의 검사 스크립트(axe-core 4.14.1 포함)를 확장과 같은 순서로 주입해 검사했습니다. 확장의 사이드 패널 화면은 쓰지 않았습니다. 마크업은 확장의 마크업 검사와 같은 html-validate 10.17.1 규칙으로 검사했습니다. 마우스와 키보드 조작은 사람이 아니라 스크립트가 보냈습니다. 규칙 수는 ‘위반 / 판정 보류 / 통과’ 순서이고, 요소 수가 아니라 규칙 종류 수입니다. on의 값은 결함 수정 뒤의 값입니다.

### 브라우저에서 관찰한 결과

- 두 화면 모두 진입하면 창이 모달 상태로 열렸고 초점은 닫기 버튼에 있었습니다.
- off에서 위반이던 `color-contrast`가 on에서는 위반과 판정 보류에 없었고, 창 열림 상태의 통과 규칙이 19개에서 20개로 늘었습니다. 창을 닫은 상태의 규칙 수는 두 화면이 같았습니다.
- 결함 수정 전의 on에서는 자동으로 열린 창을 Esc, X 버튼 클릭, 닫기 버튼의 Enter로 닫으면 세 경우 모두 초점이 `body`에 있었습니다. off와 같은 결과였습니다. 이 관찰을 on 개발 세션에 보고했습니다.
- 결함 수정 후의 on에서는 같은 세 가지 방법으로 닫으면 모두 초점이 `h1#page-title`(‘푸른숲도서관 소개’)에 있었습니다.
- 두 화면 모두 ‘이용 안내 보기’ 버튼으로 연 창을 X 버튼 클릭, 창 바깥 클릭, Esc로 닫으면 초점이 그 버튼으로 돌아왔습니다. on의 이 결과는 수정 전후가 같았습니다.
- 확장 검사의 규칙 수는 수정 전후가 같았습니다(창 열림 0 / 0 / 20, 창 닫음 0 / 0 / 12).
- 창이 열린 상태의 Tab 순서 기록은 두 화면 모두 닫기 버튼 다음이 ‘오늘 하루 보지 않기’ 체크 상자, 그다음이 `body`였습니다.
- 창이 열린 상태에서 Tab을 여섯 번 누르는 동안 초점이 있는 요소가 `dialog` 안이었던 것은 두 화면 모두 네 번입니다. 두 번째와 다섯 번째에는 `dialog` 안에 있지 않았습니다. on의 수정 전후도 같았습니다.
- 두 화면 모두 Tab으로 초점을 받은 요소마다 초점 표시가 있었습니다.
- on의 초기 상태 콘솔에 404가 1건 기록됐습니다. 브라우저를 새로 띄운 뒤 처음 연 화면이었고, 브라우저의 파비콘 요청으로 추정하지만 따로 확인하지 않았습니다.

### 코드에서 확인한 사실

- on의 `dialog`는 `body`의 첫 요소이고, 머리글과 본문은 그 뒤에 있습니다. off의 `dialog`는 본문 뒤에 있습니다.
- on의 닫기 함수는 `dialog`를 닫은 뒤 초점을 옮깁니다. 버튼으로 열었으면 그 버튼으로, 자동으로 열렸으면 `h1`로 옮깁니다. off의 스크립트에는 초점을 옮기는 코드가 없습니다.
- on의 `h1`에는 `id="page-title"`과 `tabindex="-1"`이 있습니다. `style.css`의 초점 표시 규칙은 버튼과 입력의 `:focus-visible`에만 있고, `h1`에 대한 규칙은 없습니다.
- on의 바깥 누름은 `pointerdown`에서 누른 대상이 `dialog` 자체인지 기록하고, `click`에서도 대상이 `dialog` 자체일 때만 닫습니다. off는 `click`의 대상만 봅니다.
- 창이 이미 열려 있으면 `showModal()`을 다시 부르지 않는 점은 두 화면이 같습니다. off는 `if (!dialog.open) dialog.showModal()`, on은 함수 첫 줄의 `if (dialog.open) return`으로 처리합니다. on은 이 경우 ‘오늘 하루 보지 않기’ 해제도 건너뜁니다.
- `style.css`의 차이는 세 줄입니다. 닫기 버튼의 `top`과 `right`가 4px에서 8px로, 제목의 오른쪽 여백이 40px에서 52px로, ‘오늘 하루 보지 않기’ 글자색이 `#aaaaaa`에서 `#6b6b6b`로 바뀌었습니다.
- ‘오늘 하루 보지 않기’ 저장, Esc의 `cancel` 처리, 창 안의 마크업은 off와 같습니다.

## 미검증 항목

- 스크린 리더 발화: 창이 열릴 때 제목 ‘12월 이용 안내’를 읽는지, 뒤 화면을 읽지 않는지, X 버튼을 ‘닫기’로 읽는지 확인하지 않았습니다. 창을 본문 앞으로 옮긴 효과와 `h1`으로 초점을 옮긴 뒤의 읽기 위치도 보조기술로 확인하지 않았습니다.
- 실제 터치 기기와 Chrome 이외의 브라우저에서는 확인하지 않았습니다.
- Tab을 누르는 동안 초점이 `dialog` 밖으로 기록된 순간에 초점이 실제로 어디에 있었는지 확인하지 않았습니다. Shift+Tab의 이동도 기록하지 않았습니다.
- 자동으로 열린 창을 닫은 직후 Tab을 한 번 누르면 초점이 ‘이용 안내 보기’ 버튼으로 가는지 기록하지 않았습니다. Shift+Tab으로 거꾸로 이동할 때 `h1`이 Tab 순서에 끼어들지 않는지도 기록하지 않았습니다.
- `h1`이 초점을 받았을 때 초점 표시가 보이는지 확인하지 않았습니다.
- 닫기 버튼의 초점 윤곽선이 창 가장자리에서 잘리지 않는지 확인하지 않았습니다.
- 창 안에서 누른 채 창 바깥에서 뗄 때 창이 닫히지 않는지 기록하지 않았습니다. 바깥을 클릭하면 닫히는 것만 확인했습니다.
- ‘오늘 하루 보지 않기’를 선택하고 닫은 뒤 새로고침했을 때 창이 열리지 않는지, 선택하지 않고 닫으면 다시 열리는지 확인하지 않았습니다.
- 폭 320px에서는 가로 스크롤만 확인했습니다. 창이 화면 안에 들어오는지, 스크롤로 모든 안내가 보이는지, 제목이 X 버튼과 겹치지 않는지는 확인하지 않았습니다.
- 화면 확대와 고대비 모드는 확인하지 않았습니다.

### 개발 중 읽지 못한 자료

- 조회에 실패한 주소는 없었습니다.
- 위 14개 밖의 검사항목 레코드는 읽지 않았고 적용 항목으로 적지 않았습니다. 그중 5.4.2, 6.2.1, 6.5.1은 해당하는 요소가 없다고 판단했을 뿐 레코드로 확인하지는 않았다고 보고했습니다.
- 8.2.1은 본문과 기본 규칙만 읽었고 사례 레코드는 읽지 않았습니다.
- 각 항목에 딸린 레코드 가운데 사례가 아닌 것(목적, 배경 및 필요성, 용어)은 읽지 않았습니다. 개발 에이전트는 항목 본문과 기본 규칙으로 충분하다고 판단했다고 적었습니다.
- 개발 에이전트는 요청에 없어 구현하지 않은 제안 두 가지를 적었습니다. ‘오늘 하루 보지 않기’ 글자를 14px 이상으로 키우는 것과, 닫기 버튼에 ‘닫기’ 글자를 함께 보여 주는 것입니다.
